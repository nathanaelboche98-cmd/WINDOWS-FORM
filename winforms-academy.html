Arquitectura y eventos

WinForms es un envoltorio administrado sobre Win32 y GDI+. Cada control crea una ventana nativa con su propio Handle.

Una clase, dos archivos

El diseñador solo escribe C#. Puedes crear toda la interfaz por código sin usarlo.

El bucle de mensajes

Application.Run(new Form1()) arranca el message loop del hilo de UI.

  1. Windows coloca un mensaje (clic, tecla, repintado) en la cola.
  2. El bucle lo extrae y lo envía a la ventana destino (WndProc).
  3. WinForms lo traduce a un evento .NET como Click.
  4. Se ejecuta tu manejador, suscrito con +=.
Todo corre en un solo hilo. Una consulta lenta dentro de un manejador congela la ventana. Usa async/await y toca los controles solo desde el hilo de UI.

Ciclo de vida del formulario

  1. ConstructorLlama a InitializeComponent
  2. LoadLlenar combos y configurar el grid
  3. ShownPrimera vez visible; tareas async
  4. FormClosingConfirmar o cancelar con e.Cancel
  5. FormClosedLiberar recursos

Controles principales

Pasa el cursor o toca una tarjeta para ver sus propiedades y eventos más usados. Nómbralos con prefijo: btnGuardar, txtNombre, dgvProductos.

Ejemplo: conectar los controles

El flujo clásico: leer, validar, procesar y mostrar. Usa un TextBox, un ComboBox, un Button, un DataGridView y un Label.

Form1.cs 
public record Producto(string Nombre, decimal Precio, string Categoria);

public partial class Form1 : Form
{
    // BindingList avisa al DataGridView cuando cambia
    private readonly BindingList<Producto> _productos = new();

    public Form1() => InitializeComponent();

    private void Form1_Load(object? sender, EventArgs e)
    {
        cboCategoria.DataSource = new List<string> { "Alimentos", "Bebidas", "Otros" };
        cboCategoria.DropDownStyle = ComboBoxStyle.DropDownList;
        dgvProductos.DataSource = _productos;
        dgvProductos.AutoSizeColumnsMode = DataGridViewAutoSizeColumnsMode.Fill;
    }

    private void btnAgregar_Click(object? sender, EventArgs e)
    {
        // 1. Leer y validar
        string nombre = txtNombre.Text.Trim();
        if (nombre.Length == 0)
        {
            MessageBox.Show("Escribe el nombre del producto.");
            txtNombre.Focus();
            return;
        }
        if (!decimal.TryParse(txtPrecio.Text, out decimal precio) || precio <= 0)
        {
            MessageBox.Show("Ingresa un precio válido.");
            txtPrecio.SelectAll();
            return;
        }

        // 2. Procesar
        _productos.Add(new Producto(nombre, precio, cboCategoria.Text));

        // 3. Mostrar
        lblTotal.Text = $"Total: {_productos.Sum(p => p.Precio):C}";

        // 4. Limpiar para la siguiente captura
        txtNombre.Clear();
        txtPrecio.Clear();
        txtNombre.Focus();
    }

    // Solo dígitos y un punto decimal
    private void txtPrecio_KeyPress(object? sender, KeyPressEventArgs e)
    {
        bool punto = e.KeyChar == '.' && !txtPrecio.Text.Contains('.');
        if (!char.IsControl(e.KeyChar) && !char.IsDigit(e.KeyChar) && !punto)
            e.Handled = true; // la tecla no llega al TextBox
    }
}

Separar la UI de la lógica

El ejemplo funciona, pero mezcla reglas, cálculo y presentación. Estas tres prácticas lo corrigen.

El formulario solo traduce

Un manejador lee controles, llama a un servicio y pinta el resultado. Si puedes probar el servicio sin abrir una ventana, la separación es correcta.

Capas y MVP

Separa proyectos: UI, Business, Data, Models. La UI depende de la lógica, nunca al revés. En pantallas complejas usa Model-View-Presenter con una interfaz IProductoView e inyección de dependencias en Program.cs.

Sin bloqueos ni datos en controles

Las operaciones lentas van con async/await. El estado vive en tus objetos y se sincroniza con data binding, no con comparaciones como lblEstado.Text == "Activo".

private async void btnCargar_Click(object? s, EventArgs e)
{
    btnCargar.Enabled = false;
    try { dgv.DataSource = await _repo.ObtenerAsync(); }
    finally { btnCargar.Enabled = true; }
}
